# Background: webhook-delivery

- **silent**, resilience/webhooks (`background:webhook-delivery`): Advanced Billing posts a webhook and the endpoint answers with anything other than 200 OK, or does not answer within about 15 seconds → The webhook is not accepted and is retried automatically. **Do:** Answer webhooks with 200 OK as fast as possible and do slow work after responding. *(`maxio-c4:background.1`)*
- **silent**, -/values (`background:webhook-delivery`): A webhook payload contains timestamps → Timestamps use the site's time zone (Eastern Time by default, with daylight saving), except newer events such as component_allocation_change and metered_usage, which use ISO 8601 in UTC. **Do:** Parse webhook timestamps per event type and do not assume one time zone. *(`maxio-c4:background.10`)*
- **silent**, -/webhooks (`background:webhook-delivery`): One system event happens, such as creating a subscription that needs a payment → Several webhooks can fire for it (for example signup_success and payment_success). **Do:** Handle related webhooks independently and in any order. *(`maxio-c4:background.11`)*
- **silent**, -/values (`background:webhook-delivery`): A webhook payload is built from a resource → Not every value is populated; for example reason_code and component allocations are not included in signup_success. **Do:** Treat payload fields as optional and read the resource through the API when a value is missing. *(`maxio-c4:background.12`)*
- **silent**, account-config/webhooks (`background:webhook-delivery`): The site uses the enhanced (new) Catalog experience → Webhook event names and messages change: subscription_product_change becomes subscription_plan_change, component_allocation_change becomes allocation_change, and component_billing_date_change becomes product_billing_date_change. **Do:** Handle both the old and the new event names when the catalog experience may be enabled. *(`maxio-c4:background.13`)*
- **silent**, -/webhooks (`background:webhook-delivery`): An application relies on webhooks to react to events → Webhooks are asynchronous and may arrive late, so they are not suited to time-sensitive actions. **Do:** Do not block signups or provisioning on webhooks; verify subscriptions through the API. *(`maxio-c4:background.14`)*
- **silent**, -/values (`background:webhook-delivery`): A test webhook is sent from the Webhooks Control Panel → The endpoint receives the payload id=123456&event=test&payload[chargify]=testing, which may not match production webhooks. **Do:** Accept and ignore event=test webhooks without failing. *(`maxio-c4:background.15`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A subscription's billing date changes → billing_date_change fires only for an explicit change through the application or API, not for a normal renewal, period advance or migration. **Do:** Do not use billing_date_change to track renewals. *(`maxio-c4:background.16`)*
- **silent**, -/webhooks (`background:webhook-delivery`): Component allocations are set during the initial subscription creation (signup) → component_allocation_change does not fire; it fires only for allocation, on/off or prepaid purchase changes made after signup. **Do:** Read initial allocations from the subscription, not from component_allocation_change. *(`maxio-c4:background.17`)*
- **silent**, -/values (`background:webhook-delivery`): component_allocation_change fires for an on/off component → previous_allocation and new_allocation are 0 (off) or 1 (on), and timestamp is ISO 8601 in UTC. **Do:** Read on/off component changes as 0/1 values and parse the timestamp as UTC. *(`maxio-c4:background.18`)*
- **silent**, -/webhooks (`background:webhook-delivery`): Maxio.js tokenization fails before reaching the gateway (reCAPTCHA, fraud blocking or an invalid security token) → chjs_tokenization_failure does not fire; it fires only when the gateway returns an error during POST /js/tokens. **Do:** Do not rely on chjs_tokenization_failure to see every failed tokenization. *(`maxio-c4:background.19`)*
- **silent**, resilience/webhooks (`background:webhook-delivery`): A webhook delivery keeps failing → Each webhook is attempted up to five times on a backoff schedule (about 10, 15, 90 and 180 seconds after each failure) and then given up. **Do:** Do not count on more than five delivery attempts; replay or reconcile through the API after that. *(`maxio-c4:background.2`)*
- **silent**, -/webhooks (`background:webhook-delivery`): Maxio.js tokenizes a payment profile at the gateway successfully → chjs_tokenization_success fires (public signup pages, self-service flows or other Maxio.js integrations). **Do:** Subscribe to chjs_tokenization_success to track successful tokenizations. *(`maxio-c4:background.20`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A new customer is created → customer_create fires. **Do:** Subscribe to customer_create to sync new customers. *(`maxio-c4:background.21`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A subscription and its customer are deleted together → customer_delete does not fire; it fires only when the customer alone is explicitly deleted. **Do:** Do not rely on customer_delete to learn of customers removed together with subscriptions. *(`maxio-c4:background.22`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A customer field changes → customer_update fires only for first_name, last_name, organization, email, reference, address, address 2, city, state, zip, country, phone, vat_number, parent_id and cc_email. **Do:** Poll or read the customer for changes to other fields. *(`maxio-c4:background.23`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A delayed subscription is created, or its creation fails → delayed_subscription_creation_success (subscription in awaiting signup state) or delayed_subscription_creation_failure fires. **Do:** Subscribe to both delayed creation events when using delayed signups. *(`maxio-c4:background.24`)*
- **silent**, account-config/webhooks (`background:webhook-delivery`): A direct debit payment is created, paid out or rejected at the gateway → direct_debit_payment_pending, direct_debit_payment_paid_out and direct_debit_payment_rejected fire only for Stripe and GoCardless. **Do:** Do not expect direct debit webhooks on other gateways. *(`maxio-c4:background.25`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A pending payment is created, completed or rejected at the gateway → pending_payment_created, pending_payment_completed or pending_payment_failed fires. **Do:** Wait for pending_payment_completed or pending_payment_failed before treating a pending payment as settled. *(`maxio-c4:background.26`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A subscription's existing expiration_date changes → expiration_date_change fires. **Do:** Subscribe to expiration_date_change to track expiration dates. *(`maxio-c4:background.28`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A card on a subscription expires in the current month → expiring_card is sent periodically on the 1st, the 15th and 7 days before the end of the month. **Do:** Expect up to three expiring_card webhooks per card per month and de-duplicate reminders. *(`maxio-c4:background.29`)*
- **silent**, idempotency/webhooks (`background:webhook-delivery`, `client.WebhooksApi.ListWebhooks`, `client.WebhooksApi.ReplayWebhooks`): A webhook is retried or replayed → The webhook keeps the same id across retries and replays, so the same event can arrive more than once with one id. **Do:** Record processed webhook ids and skip ones already handled. *(`maxio-c4:background.3`)*
- **silent**, account-config/webhooks (`background:webhook-delivery`): An invoice is issued for a subscription → invoice_issued fires on Relationship Invoicing sites. **Do:** Use invoice_issued only on Relationship Invoicing sites. *(`maxio-c4:background.30`)*
- **silent**, -/webhooks (`background:webhook-delivery`): An invoice moves into the pending state → invoice_pending fires, with subscription null when the invoice has no subscription. **Do:** Handle invoice_pending payloads with and without a subscription. *(`maxio-c4:background.31`)*
- **silent**, -/webhooks (`background:webhook-delivery`, `background:renewal`): A metered component's unit balance is reset to 0 at renewal → metered_usage does not fire for the reset; it fires for reported usage, with timestamp in UTC. **Do:** Do not expect a metered_usage webhook at each renewal reset. *(`maxio-c4:background.32`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A payment is attempted (renewal, one-time charge, retry after failure, or payment applied to an invoice) → payment_success or payment_failure fires for every attempt; payment_success means only that the attempt did not fail immediately. **Do:** Handle payment webhooks for every attempt, not only renewals. *(`maxio-c4:background.33`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A payment is made by ACH/eCheck or direct debit → A payment reported by payment_success may fail later. **Do:** Do not treat payment_success for ACH/eCheck or direct debit as final. *(`maxio-c4:background.34`)*
- **silent**, account-config/values (`background:webhook-delivery`, `background:payments`): The site's payment gateway is Authorize.Net → Payment webhooks carry an extra gateway_response with approval_code. **Do:** Treat gateway_response as optional and gateway-specific. *(`maxio-c4:background.35`)*
- **silent**, account-config/values (`background:webhook-delivery`): refund_success or refund_failure webhooks are sent on sites created after the change of 18 May 2023 → The payload no longer has subscription_id; the subscription id is in the nested subscription hash. Existing sites are unaffected. **Do:** Read the subscription id from payload[subscription][id] and fall back to subscription_id only on older sites. *(`maxio-c4:background.36`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A subscription is canceled with delay (cancel at end of period), or the pending cancellation is cleared → pending_cancellation_change fires. **Do:** Subscribe to pending_cancellation_change to track scheduled cancellations. *(`maxio-c4:background.37`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A prepaid subscription's usage or prepayment balance changes → prepaid_subscription_balance_change fires. **Do:** Subscribe to prepaid_subscription_balance_change for prepaid balances. *(`maxio-c4:background.38`)*
- **silent**, -/webhooks (`background:webhook-delivery`): The allocation of a prepaid component changes → The change is reported by component_allocation_change, not prepaid_usage (which covers recorded usage). **Do:** Listen to component_allocation_change for prepaid allocation changes. *(`maxio-c4:background.39`)*
- **silent**, -/values (`background:webhook-delivery`, `client.WebhooksApi.ListWebhooks`): A webhook that failed earlier is retried or resent and then accepted → last_error and last_error_at are cleared. **Do:** Do not rely on last_error to keep the history of failed attempts. *(`maxio-c4:background.4`)*
- **silent**, -/webhooks (`background:webhook-delivery`, `background:renewal`): A recurring interval ends for a subscription → Exactly one renewal_success or renewal_failure fires. **Do:** Expect one renewal event per interval. *(`maxio-c4:background.40`)*
- **silent**, state/webhooks (`background:webhook-delivery`, `background:renewal`): A renewal failed and a later payment brings the account current → No renewal_success fires; payment_success and subscription_state_change fire instead. **Do:** Detect recovery after renewal_failure from payment_success and subscription_state_change. *(`maxio-c4:background.41`)*
- **silent**, state/webhooks (`background:webhook-delivery`, `background:renewal`): A subscription renews while it is past due → Renewal webhooks are still triggered. **Do:** Handle renewal webhooks for past-due subscriptions. *(`maxio-c4:background.42`)*
- **silent**, state/webhooks (`background:webhook-delivery`, `background:renewal`, `background:dunning`): A subscription is in dunning after its first dunning attempt → Renewal webhooks trigger only on the normal renewal dates, not daily. **Do:** Do not treat dunning retries as renewals. *(`maxio-c4:background.43`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A subscription is created through the API, the application or Public Pages → signup_success fires. **Do:** Expect signup_success also for subscriptions your own API calls create. *(`maxio-c4:background.44`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A signup fails because of input validation errors → signup_failure is not generated; it is usually caused by a failure at the payment gateway. **Do:** Handle validation failures from the API response, not from signup_failure. *(`maxio-c4:background.45`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A subscription adds or updates a bank account → subscription_bank_account_update fires. **Do:** Subscribe to subscription_bank_account_update for bank account changes. *(`maxio-c4:background.46`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A PayPal account is added, or a bank account / ACH payment profile is changed or deleted → subscription_card_update does not fire; it covers changes to the active credit card type payment profile, including partial updates and PayPal deletions. **Do:** Do not rely on subscription_card_update for PayPal additions or bank account changes. *(`maxio-c4:background.47`)*
- **silent**, -/webhooks (`background:webhook-delivery`): The active credit card payment profile of a subscription group changes → subscription_group_card_update fires. **Do:** Subscribe to subscription_group_card_update for group payment changes. *(`maxio-c4:background.48`)*
- **silent**, -/webhooks (`background:webhook-delivery`, `client.SubscriptionGroups.SignupWithSubscriptionGroup`): A subscription group signup through the Subscription Group Signup endpoint succeeds or fails → subscription_group_signup_success or subscription_group_signup_failure fires. **Do:** Subscribe to both group signup events when using group signups. *(`maxio-c4:background.49`)*
- **silent**, state/webhooks (`background:webhook-delivery`): An endpoint has failed 26 to 50 times → The endpoint is paused: webhooks are generated in a paused state and must be sent manually from the webhooks panel. **Do:** Monitor endpoint failures and resend paused webhooks once the endpoint is fixed. *(`maxio-c4:background.5`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A subscription's service credit balance changes (credit applied, or used for payment) → subscription_service_credit_account_balance_changed fires. **Do:** Subscribe to subscription_service_credit_account_balance_changed for service credit balances. *(`maxio-c4:background.51`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A subscription moves to a new product version → subscription_product_change fires, as it does for a change to another product. **Do:** Expect subscription_product_change also for product version changes. *(`maxio-c4:background.52`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A delayed product change is scheduled for a subscription → subscription_product_change_scheduled fires as soon as the change is created, before it takes effect at renewal. **Do:** Use subscription_product_change_scheduled to react to upcoming product changes. *(`maxio-c4:background.53`)*
- **silent**, -/webhooks (`background:webhook-delivery`): A subscription's state changes → subscription_state_change fires with both previous_state and state in the subscription object. **Do:** Track subscription state through subscription_state_change and compare previous_state with state. *(`maxio-c4:background.54`)*
- **silent**, -/webhooks (`background:webhook-delivery`, `background:renewal`): A subscription is 3 days from renewing → upcoming_renewal_notice fires. **Do:** Use upcoming_renewal_notice for pre-renewal reminders. *(`maxio-c4:background.55`)*
- **silent**, -/webhooks (`background:webhook-delivery`): An upgrade or downgrade succeeds or fails → upgrade_downgrade_success or upgrade_downgrade_failure fires. **Do:** Subscribe to both upgrade/downgrade events. *(`maxio-c4:background.56`)*
- **silent**, -/webhooks (`background:webhook-delivery`, `background:renewal`): A statement closes at the end of a period and payment was received or not required → statement_settled fires. **Do:** Treat statement_settled as the paid outcome of a period. *(`maxio-c4:background.57`)*
- **silent**, -/webhooks (`background:webhook-delivery`, `background:renewal`): A statement closes at the end of a period without successful payment → statement_closed fires, and statement_settled may follow later if the statement becomes paid (for example after a dunning retry or card update). **Do:** Keep statement state open after statement_closed and update it on a later statement_settled. *(`maxio-c4:background.58`)*
- **silent**, state/webhooks (`background:webhook-delivery`): An endpoint is paused → The endpoint is checked every two hours and re-enabled if it responds. **Do:** Expect a paused endpoint to resume on its own once it answers again. *(`maxio-c4:background.6`)*
- **silent**, state/webhooks (`background:webhook-delivery`): An endpoint has failed 51 times or more → The endpoint is disabled and webhooks are no longer generated for it. **Do:** Keep endpoints healthy and reconcile through the API if an endpoint was disabled. *(`maxio-c4:background.7`)*
- **silent**, -/values (`background:webhook-delivery`): A webhook is delivered → It is an HTTP POST with Content-Type application/x-www-form-urlencoded whose payload keys use square-bracket notation. **Do:** Accept form-encoded POST bodies on webhook endpoints and parse bracketed keys. *(`maxio-c4:background.8`)*
- **silent**, auth/webhooks (`background:webhook-delivery`): A webhook is received → It is signed with HMAC-SHA-256 over the raw body using the site's shared key, sent in the X-Chargify-Webhook-Signature-Hmac-Sha-256 header or in the query string via {signature_hmac_sha_256}. **Do:** Verify the HMAC-SHA-256 signature against the raw body with the site shared key before acting on a webhook. *(`maxio-c4:background.9`)*
- **silent**, -/webhooks (`client.SubscriptionInvoiceAccount.CreatePrepayment`, `client.Invoices.RecordPaymentForInvoice`, `client.Invoices.RecordPaymentForSubscription`, `client.Invoices.RecordPaymentForMultipleInvoices`, `client.SubscriptionInvoiceAccount.RefundPrepayment`, `background:webhook-delivery`): A subscription's prepayment account balance changes (prepayment added, or used to pay an invoice) → A subscription_prepayment_account_balance_changed webhook is sent. **Do:** Listen for subscription_prepayment_account_balance_changed to keep prepayment balances in sync. *(`maxio-c4:createPrepayment.4`)*
